# 项目章程（Project Charter）

## 1. 项目概述
- 项目名称：空气质量 / 天气联动分析看板
- 项目类型：轻量级数据处理 Web 应用
- 项目定位：围绕城市环境监测场景，聚合天气与空气质量数据，通过独立算法接口完成风险评分与异常检测，并以可视化看板方式展示分析结果。

## 2. 项目背景
本项目来源于“基于 AI 工具 Skills 的数据处理应用开发”任务，目标是在可控时间内完成一个具备企业项目规范的数据处理系统。相比纯展示型页面，本项目强调：
- 外部数据接入能力
- 算法服务调用能力
- 工作流编排能力
- 文档、测试、审查的闭环能力

空气质量与天气数据具有公开、结构化、稳定、易展示的特点，适合作为本项目的 MVP 场景。

## 3. 业务目标
### 3.1 总体目标
构建一个可以根据城市维度展示天气与空气质量联动情况的分析看板，形成“数据获取 -> 数据标准化 -> 风险分析 -> 可视化展示”的完整链路。

### 3.2 具体目标
- 接入至少 1 个天气数据接口与 1 个空气质量数据接口。
- 提供至少 1 个独立网络算法接口，用于风险评分或异常检测。
- 提供可配置工作流，支持切换城市、调整算法参数、执行分析流程。
- 使用可追溯的 Figma / UI 组件来源完成前端界面。
- 输出完整文档、测试计划、AI Skills 使用记录和代码审查记录。

## 4. MVP 范围
### 4.1 In Scope
- 城市选择与查询
- 天气数据拉取
- 空气质量数据拉取
- 天气 / AQI 联动分析
- 风险评分展示
- 异常检测结果展示
- 24 小时趋势图与未来 7 天趋势摘要
- 工作流配置文件驱动执行
- 加载态、空态、错误态处理
- 项目文档、测试计划、审查记录

### 4.2 Out of Scope
- 登录 / 用户系统
- 复杂权限控制
- 持久化历史数据库
- WebSocket 实时推送
- 复杂 GIS 空间分析
- 商业级部署与监控告警平台

## 5. 目标用户
- 演示评审人员：关注系统是否完整、是否符合题目要求
- 开发者 / 面试官：关注架构规范、代码分层、扩展能力
- 一般业务查看者：关注城市空气质量风险是否直观易懂

## 6. 核心使用场景
1. 用户选择目标城市。
2. 系统并行获取天气数据与空气质量数据。
3. 系统对数据进行标准化、校验和组装。
4. 系统调用算法接口完成风险评分与异常检测。
5. 前端展示当前风险、趋势变化与预警提示。

## 7. 成功标准
- 可成功接通外部数据接口并返回结构化结果。
- 可成功调用独立算法接口并返回风险评分结果。
- 工作流可通过配置文件驱动，而不是硬编码。
- 前端可展示天气、AQI、风险等级、趋势图、异常提示。
- 项目交付物完整，包括代码、配置、文档、skills 文件、AI 记录与审查报告。

## 8. 关键假设
- 可使用公开天气与空气质量 API，且无需复杂付费鉴权。
- Figma 或公开 UI 设计资源可用于风格参考与组件复用说明。
- 风险评分可采用规则模型或轻量算法模型，不要求复杂机器学习训练。
- 当前阶段重点是可运行、可演示、可交付，而非生产级高可用架构。

## 9. 主要风险与应对
| 风险 | 影响 | 应对策略 |
|---|---|---|
| 外部 API 不稳定或字段变化 | 接口联调失败 | 预留 mock / fallback 响应，并在适配层统一映射 |
| 风险评分逻辑不够清晰 | 结果可解释性不足 | 输出明确评分规则文档，保留阈值可配置 |
| Figma 来源不明确 | 无法满足题目复用要求 | 优先选择公开 Figma 社区模板，并留存链接或截图 |
| 地图、热力图导致范围失控 | 项目延期 | 地图功能列入增强项，MVP 只做卡片与趋势图 |
| 前后端字段不一致 | 联调成本高 | 先冻结数据契约，再推进前后端开发 |

## 10. 验收标准
- 至少 1 个天气 / 空气质量数据接口完成接入。
- 至少 1 个独立算法接口可调用。
- 至少 1 组 Figma 组件来源和映射说明完整。
- 工作流支持参数配置与执行。
- 项目具备分层架构与异常处理。
- 测试计划、AI Skills 记录、代码审查报告齐全。
- 提供 README、运行说明和 `.env.example`。

- M3：工程骨架与后端 MVP 完成

- M5：测试、审查与交付封板完成
